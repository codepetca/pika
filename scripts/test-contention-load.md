# Disposable learner contention load

This manual harness exercises the current branch's `createContextualTestLearnerWorkflow` with the actual Supabase SDK and a synthetic class. It runs student session and paired detail reads, then concurrently starts, saves and submits one distinct answer per learner, checks every submitted answer in the database, and removes its fixture. A real owner workflow inspect runs concurrently with every student phase. Each phase reports student success/failure counts, the concurrent owner-read result, elapsed time, and RPC error counts grouped by code, allowlisted message, and HTTP status. It does not exercise HTTP route handling, browser behavior, history writes, or prove production capacity.

Prerequisites: a separately provisioned disposable clone with the reviewed schema including migrations 256 and 257 already applied; an independent PostgREST service configured for that clone; Docker and `psql` inside the database container. This harness never applies migrations. Do not point it at the shared local Supabase stack or any non-disposable data. Both containers must be running and labeled with the same randomly generated 32-character lowercase hexadecimal owner token, using `pika.test-load.owner=<token>` and respectively `pika.test-load.role=db` and `pika.test-load.role=api`. The PostgREST image must be `postgrest/postgrest`, its service role must have execute privileges on the owner and learner workflow RPCs; its `PGRST_DB_URI` must name the labeled DB on a shared Docker network and target database `postgres`, and its port 3000 must be bound only to `127.0.0.1:54331`. Database must permit `docker exec` as postgres. Set `TEST_LOAD_SERVICE_KEY` to the service-role JWT accepted by that PostgREST instance. Do not put credentials in command arguments or logs.

Run from this worktree with 2–40 learners:

```sh
TEST_LOAD_SERVICE_KEY='<disposable service-role JWT>' pnpm exec tsx scripts/test-contention-load.ts '<full DB container ID>' '<full API container ID>' '<owner token>' 30
```

For standalone PostgREST, the harness maps the SDK gateway path to the matching direct RPC path. It reports only allowlisted RPC error messages and constrained codes, aggregated by phase. The API port, labels, image, network, DB URI and IDs are checked before fixture creation, final verification and cleanup. The fixture is committed to permit independent concurrent requests. Cleanup runs after success or failure and verifies its user and classroom rows are absent. If the process is killed, target verification fails, or cleanup reports an error, destroy the entire disposable clone and API container; do not retry against another target. A load failure can leave requests already dispatched in flight; dispose of the target after the process exits. Neither a mock run nor an unexecuted harness is load evidence.
