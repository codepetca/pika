# Verified public classroom admission

This is a disabled-by-default implementation candidate, not a production rollout receipt. The public-admission policy, the master growth control and the server caller switch must all be enabled before a verified nonadmitted account can be admitted. Existing registry grants remain usable while growth is stopped. A master stop also clears the public policy, so reopening operator growth does not reopen public admission.

Admission selects the classroom experience; it does not join a classroom, alter a plan, create ownership or grant a provider capability. The existing classroom membership, entitlement and provider checks remain authoritative. Bara protocol compatibility remains bound to the original bootstrap origin; a new automatic grant is not a bootstrap grant. Preserve the existing protected account exclusion and Pal profile-erasure pathway.

A service-only database operation checks the canonical local user's verified email, protected exclusion and registry state. It serializes grant and stop operations on the existing policy lock, creates at most one immutable grant per user and returns an existing grant without rewriting its origin. Unknown write outcomes require a fresh read before any retry. An advisory read may offer an already-signed-in, eligible user an explicit action; it cannot create a grant, and the action rechecks eligibility atomically. Authenticated session creation can request the same operation only after the server has resolved the identity. The sign-in itself remains available if admission is unavailable.

Before any rollout, review the actual identity, registry, account-deletion and provider effects; run the full schema, security, concurrency, UI and CI proofs against the exact candidate. Verify email delivery, signup/join abuse controls and realistic admission contention. Check the canonical deployment, migrations, existing grants, exclusion and settings afresh. New grants should stop on an unexpected privacy or authorization failure; preserve admitted users, routing and data. Paid subscriptions, provider enablement and production migrations require their own authorization and readiness evidence.

Migration 330 removes an account’s live grant when an authorized deletion of the corresponding `public.users` row succeeds. Historical batch receipts, including their committed counts, remain available. Direct grant updates and removal are rejected while the account exists. An admitted owner must resolve all owned classrooms, including cold archives, before deleting the account. Protected exclusions and existing deletion safeguards still apply. This migration supplies the registry portion of account deletion. Account, classroom, and provider cleanup continue through their respective authorized procedures.

## Launch alerts

Pika records separate production diagnostics for unexpected WorkOS code issuance or delivery failures and classroom admission registry failures. Pika passes only the failure category to the alert receiver after responding to the caller.

The dormant `workers/classroom-launch-alerts` Worker can send to one verified operations inbox through Cloudflare Email Service. Configure the sender and recipient as `PIKA_LAUNCH_ALERT_FROM` and `PIKA_LAUNCH_ALERT_TO`, and restrict the `ALERT_EMAIL` binding to that verified destination in the deployment configuration. Use an onboarded sending domain. If using a dedicated subdomain, verify the DNS changes apply there so the root domain continues to use its existing mail service.

Use the same generated 32-byte hex token as `PIKA_LAUNCH_ALERT_TOKEN` in Vercel production and the Worker. The Vercel `PIKA_LAUNCH_ALERT_ORIGIN` is the Worker’s HTTPS origin. Enable `PIKA_LAUNCH_ALERTS_ENABLED` on the Worker after the mail binding and HTTPS route are ready. The shared token and deployment values belong in provider configuration. The receiver groups each category for 30 minutes and retries failed sends using a Durable Object alarm.

With admission closed, make one authenticated POST to `/v1/launch-alerts/canary` and confirm the labeled message reaches the intended inbox. HTTP 202 confirms the receiver accepted the request. Review `classroom.launch.alert_delivery` in Vercel and the Worker’s alarm logs if delivery fails. Check uptime monitoring for a complete Vercel outage and Brevo’s delivery records for mail delayed after acceptance.
