# Verified public classroom admission

This is a disabled-by-default implementation candidate, not a production rollout receipt. The public-admission policy, the master growth control and the server caller switch must all be enabled before a verified nonadmitted account can be admitted. Existing registry grants remain usable while growth is stopped. A master stop also clears the public policy, so reopening operator growth does not reopen public admission.

Admission selects the classroom experience; it does not join a classroom, alter a plan, create ownership or grant a provider capability. The existing classroom membership, entitlement and provider checks remain authoritative. Bara protocol compatibility remains bound to the original bootstrap origin; a new automatic grant is not a bootstrap grant. Preserve the existing protected account exclusion and Pal profile-erasure pathway.

A service-only database operation checks the canonical local user's verified email, protected exclusion and registry state. It serializes grant and stop operations on the existing policy lock, creates at most one immutable grant per user and returns an existing grant without rewriting its origin. Unknown write outcomes require a fresh read before any retry. An advisory read may offer an already-signed-in, eligible user an explicit action; it cannot create a grant, and the action rechecks eligibility atomically. Authenticated session creation can request the same operation only after the server has resolved the identity. The sign-in itself remains available if admission is unavailable.

Before any rollout, review the actual identity, registry, account-deletion and provider effects; run the full schema, security, concurrency, UI and CI proofs against the exact candidate. Verify email delivery, signup/join abuse controls and realistic admission contention. Check the canonical deployment, migrations, existing grants, exclusion and settings afresh. New grants should stop on an unexpected privacy or authorization failure; preserve admitted users, routing and data. Paid subscriptions, provider enablement and production migrations require their own authorization and readiness evidence.

The existing registry grants reference `public.users` and are immutable. Its current contract has no admission-removal or account-deletion path. Public activation must not be represented as account-deletion readiness: design and review the affected lifecycle before attempting deletion; do not bypass the foreign key or delete grants as a rollout rollback.
